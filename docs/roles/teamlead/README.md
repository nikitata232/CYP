# CYP — задание участнику TeamLead

**Рабочая ветка участника:** `feature/TeamLead`. Документы с заданиями подготовлены в `docs`.

Основа — [общая спецификация](../../../README.md). Цель роли — довести согласованные части до работающего MVP: заказ → выручка и затраты → прибыль и маржа → отчёт. TeamLead отвечает за общие решения, зависимости, интеграцию и проверяемую готовность, а не только распределение задач.

## Исходное состояние

На момент подготовки заданий в проекте есть общая спецификация; кода приложения, миграций, конфигурации запуска и автоматических проверок ещё нет. Четыре рабочие ветки созданы от одного коммита. Наличие ветки или предложенной технологии не означает готовность компонента.

## Ответственность команды

| Направление | Основной исполнитель | Участники согласования |
|---|---|---|
| Бизнес-правила и границы MVP | TeamLead с владельцем продукта | Все затронутые роли |
| Контракт API | Backend | Frontend, DB; принятие TeamLead |
| HTTP, сервисы и канонические расчёты | Backend | DB по точности и источникам данных |
| Схема, ORM-модели и миграции | DB | Backend |
| Аналитические выборки, агрегаты, индексы | DB | Backend; приёмка TeamLead |
| Интерфейс и клиентское состояние | Frontend | Backend |
| Общая инфраструктура, CI и интеграция | TeamLead | Исполнители компонентов |
| Сквозная приёмка и документация запуска | TeamLead | Все роли |

Задания участников: [Backend](../backend/README.md), [Frontend](../frontend/README.md), [DB и аналитика](../db/README.md).

## TL1. Закрыть открытые решения

До реализации зависимых частей:

1. Проверить с владельцем продукта рабочие допущения раздела 12: статусы, отчёт по дате завершения, исправление завершённых заказов, ручное отнесение общих расходов и одного оператора.
2. Зафиксировать стек и совместимые версии в файлах зависимостей и документации. Не переносить версии DebtFree автоматически.
3. Определить размещение и модель доступа: локальный режим или защищённый сервер. Не добавлять регистрацию и роли по инерции из другого проекта; реализовать необходимый выбранному режиму доступ до сетевого размещения.
4. Зафиксировать часовой пояс мастерской; рабочее значение спецификации — Europe/Moscow.
5. Определить стратегию резервного копирования с DB до ввода реальных данных.

Решения документировать с датой, причиной и влиянием на контракты/проверки. Изменения продукта отражать в основном README. Не считать этот список основанием остановить подготовку независимых компонентов.

## TL2. Организовать договорённости между ролями

Обеспечить появление следующих артефактов; названные файлы пока являются планом:

| Артефакт | Готовит | Что принимает TeamLead |
|---|---|---|
| `docs/api-contract.md` | Backend с Frontend и DB | Методы, схемы, денежные строки, маржа/null, даты, фильтры, ошибки и примеры |
| `docs/data-model.md` | DB с Backend | Типы, ограничения, связи, индексы, нумерация и владение моделями |
| `docs/analytics.md` | DB с Backend | Выборка, показатели, агрегация, согласованность строк/итогов и проверочные данные |
| Фиксация архитектурных решений | TeamLead с исполнителями | Стек, доступ, инфраструктура, тестовое окружение |

Особенно проверить границу аналитики: DB строит корректные строки и исходные общие суммы; Backend применяет общий расчётный модуль и публикует HTTP-ответ; Frontend отображает готовые показатели. Не должно появиться трёх независимых реализаций общей маржи.

## TL3. Управлять последовательностью работ

1. **Контракты и основа:** зафиксировать общие правила, структуру каталогов, API, интерфейс аналитического слоя и модель данных.
2. **Независимая работа:** DB готовит схему/миграции/фикстуры; Backend — серверную основу/расчёты; Frontend — навигацию/формы/состояния по контракту.
3. **Первый сквозной сценарий:** подключить БД и реальный API, создать клиента и заказ, добавить затраты, получить прибыль в карточке.
4. **Статусы и аналитика:** завершить заказ, получить отчёт, проверить даты, нулевую выручку и общую маржу.
5. **Исправления и надёжность:** возобновление, обновление завершённых заказов, ошибки, перезапуск, актуальность всех экранов.
6. **Приёмка:** чистое окружение, миграции, сборка, все контрольные проверки, проверенная инструкция.

Для задачи фиксировать исполнителя, ожидаемый результат, зависимости и доказательство готовности. Согласовать точные имена веток: в Git существуют `feature/backend`, `feature/frontend`, `feature/DB`, `feature/TeamLead`. Не создавать случайно другие варианты регистра.

Не переименовывать, не перезаписывать ветки и не публиковать изменения без соответствующего разрешения владельца репозитория. Документы ролей подготовлены в `docs`; получение их участниками согласовать отдельно. Пока нет коммита, файлы существуют только в локальном рабочем дереве.

## TL4. Владеть общими файлами и инфраструктурой

- Общие Docker Compose, nginx, `.env.example`, `.gitignore`, CI и корневую документацию интегрирует TeamLead. Исполнители готовят требования и изменения компонентов; не поддерживать конфликтующие версии общих конфигураций.
- DB владеет `backend/app/models/` и `backend/migrations/`; Backend согласует импорт и сессии до начала реализации. Остальные серверные области принадлежат Backend, клиентский код — Frontend.
- Настроить воспроизводимый запуск с постоянным хранением БД, применением миграций и корректным порядком готовности сервисов.
- Отделить тестовое окружение и БД от пользовательских данных. Автоматические проверки не должны очищать рабочую БД.
- Собирать конфигурацию из переменных; коммитить только безопасные примеры, без ключей и реальных контактов.
- Настроить согласованные проверки сборки, типов/стиля, модульных и интеграционных тестов. Конкретные инструменты выбирать по принятому стеку.
- Убедиться, что режим доступа и сетевые настройки соответствуют выбранному размещению.

## TL5. Проверить интеграцию и принять MVP

### Матрица проверок

| Проверки основного README | Кто предоставляет доказательство | Кто принимает |
|---|---|---|
| T1–T7: формулы, точность и округление | Backend; DB сверяет данные | TeamLead |
| T8–T14: отчёт, даты, статусы и исправления | DB + Backend; Frontend проверяет отображение | TeamLead |
| T15: ошибки и отсутствие частичных записей | Backend + DB | TeamLead |
| T16: сохранность после перезапуска | DB + Backend, инфраструктура TeamLead | TeamLead |
| T17: ошибка формы без потери ввода | Frontend с Backend | TeamLead |
| UC-1–UC-6 и F1–F10 целиком | Все участники | TeamLead |

Проверять не только ответы отдельных модулей: одинаковый заказ должен иметь одинаковые суммы в карточке, списке и отчёте. После изменения завершённого заказа обновление должно доходить до UI. Общая маржа примера с двумя заказами — 28,33%, а не 37%.

Отдельно принять отсутствие умножения выручки при JOIN нескольких затрат, включение заказов без затрат, нулевую выручку, обе границы периода, исключение отменённых/возобновлённых заказов и итоги по всей выборке.

### Порядок интеграции

При разрешённой работе с коммитами/PR проверять состав изменений, тесты и совместимость контракта до объединения. Миграции должны образовывать единую цепочку. После интеграции запускать сквозной сценарий на общем состоянии проекта. Не принимать компонент только по скриншоту или успешному тесту с моками.

## Что передать владельцу проекта

- Работающий MVP и актуальную общую спецификацию с фактическим статусом функций.
