# CYP — задание участнику DB и аналитика

**Рабочая ветка участника:** `feature/DB`. Документы с заданиями подготовлены в `docs`.

Основа — [общая спецификация](../../../README.md), особенно разделы 3, 4, 6 и 8. Ответственность роли включает **и базу данных, и аналитику по заказам**. Технологии пока предложены; до реализации их фиксирует [TeamLead](../teamlead/README.md) с командой.

## Результат работы

Воспроизводимая схема хранения клиентов, заказов и затрат, управляемые миграции и аналитический слой, который возвращает правильные строки и итоги отчёта. Отчёт учитывает завершённые заказы за период и не завышает выручку при нескольких строках затрат.

## Ответственность и границы

| Область | Владелец |
|---|---|
| Физическая схема, ограничения, индексы и нумерация заказов | DB |
| ORM-модели, базовая конфигурация метаданных и миграции | DB; интерфейс подключения согласуется с Backend |
| Аналитические выборки, агрегации и интеграционные тесты | DB |
| Канонические формулы и округление показателей на Decimal | Backend при совместной проверке DB |
| HTTP-контракт отчёта и проверка входного периода | Backend совместно с DB |
| Представление отчёта, даты фильтра и форматирование | Frontend |
| Приёмка правил аналитики, интеграция и инфраструктура | TeamLead |

DB реализует аналитический слой в серверном проекте, а не отдельный отчёт вне приложения. [Backend](../backend/README.md) вызывает этот слой через согласованный интерфейс. Не создавать второй сервер, собственные HTTP-маршруты или независимую трактовку маржи.

## Порядок выполнения

### DB1. Спроектировать физическую схему

- Перевести логические `Client`, `WorkOrder`, `CostItem` в физические таблицы со стабильными именами, первичными и внешними ключами.
- Зафиксировать в будущем `docs/data-model.md` типы, nullable-поля, значения по умолчанию, ограничения, индексы и связи. Это ожидаемый артефакт, а не уже существующий файл.
- UUID использовать для связей; номер заказа — отдельное уникальное положительное значение, назначаемое sequence/identity или эквивалентным безопасным механизмом. Не использовать `MAX(number) + 1` и не обещать отсутствие пропусков.
- Для исходных сумм выбрать точный NUMERIC/DECIMAL, поддерживающий до 999 999 999,99 ₽. Защитить допустимые диапазоны: выручка неотрицательна, затраты строго положительны.
- Проверка лишних десятичных знаков выполняется Backend до записи: NUMERIC с scale 2 может округлять вход сам и не заменяет эту валидацию.
- Для `SUM` и промежуточных результатов использовать типы/точность, не ограниченные максимумом одной строки. Не приводить агрегат обратно к узкому типу исходной суммы.
- Определить допустимые статусы и категории, обязательные поля, ограничения длин, непустое имя/название/описание затрат и минимум один непустой контакт клиента.
- Защитить согласованность `completed_on`: дата задана ровно для `completed`. Допустимый диапазон относительно создания и сегодняшнего дня проверяет Backend с учётом часового пояса мастерской.
- `created_at`/`updated_at` хранить с поддержкой UTC; `completed_on` — календарная дата. Согласовать единственного ответственного за обновление временных полей, не дублировать конфликтующие триггеры и сервисную логику.
- Не вводить уникальность телефонов/контактов и не добавлять каскадное удаление клиентов/заказов: таких операций в MVP нет. Удаление строки затрат должно работать.
- Не хранить прибыль, маржу и общие затраты как независимо редактируемые поля.

### DB2. Создать миграции и согласовать подключение

1. Владеть единой цепочкой миграций в будущем `backend/migrations/` и моделями в `backend/app/models/`; расположение уточнить с Backend до первых изменений.
2. Реализовать создание схемы на пустой БД и документированный переход между версиями. Откат проверять на тестовой БД с указанием, какие данные он уничтожает.
3. Не смешивать демонстрационные данные со структурными миграциями. Подготовить отдельное повторяемое наполнение вымышленными клиентами и заказами.
4. Передать Backend модели, правила подключения, ограничения и обработку конфликтов целостности; не оставлять ручные SQL-шаги, отсутствующие в инструкции.
5. Передать TeamLead требования к сервису БД, переменным, постоянному тому, готовности сервиса и отдельной тестовой БД.

### DB3. Реализовать аналитику

Документировать набор показателей и запросы в будущем `docs/analytics.md`, согласовав его с Backend и TeamLead.

**Состав отчёта:**

- Включать только `completed`, если `completed_on` находится между начальной и конечной датами включительно.
- Возвращать номер, название, клиента, дату завершения, выручку и сумму затрат каждого заказа; Backend добавляет прибыль и маржу общим расчётным модулем.
- Сортировать по дате завершения по убыванию, затем по номеру по убыванию.
- Возвращать количество заказов и точные общие суммы выручки/затрат по всей выборке; итоговые прибыль и маржа формируются Backend из этих сумм.
- Заказы без затрат сохранять в выборке с затратами 0. Заказы с нулевой выручкой включать в количество и затраты; общая маржа при нулевой выручке — `null`.
- Затраты брать целиком по заказу, независимо от даты создания строки. Отменённые и возобновлённые заказы исключать без удаления их данных.
- После исправления завершённого заказа отчёт отражает новые суммы и дату. Не вводить отчётные снимки или закрытые периоды.

**Защита от ошибок агрегации:**

1. Сначала агрегировать затраты по заказу, затем присоединять их к заказам либо использовать эквивалентный проверенный запрос. Обычный JOIN с несколькими затратами не должен умножать выручку и количество заказов.
2. Не усреднять проценты строк. Общая маржа — общая прибыль / общая выручка × 100.
3. Использовать `COALESCE` или эквивалент для отсутствующих затрат и пустых денежных итогов; защищать деление на ноль.
4. Не считать отчёт по текущей странице. Если пагинация добавлена, общий набор фильтров должен быть одинаковым для строк и итогов.
5. Обеспечить согласованное состояние строк и итогов при чтении: например, одним запросом или транзакцией с подходящим уровнем изоляции. Конкретный способ описать и согласовать с Backend.
6. Все входные значения передавать параметрами; не подставлять поисковый текст или даты конкатенацией SQL.

### DB4. Проверить запросы и эксплуатацию

- Подобрать индексы для внешних ключей, отбора по статусу/дате завершения и согласованной сортировки; оценить планы запросов на представительном тестовом наборе.
- Проверить поиск без учёта регистра совместно с Backend. Не обещать ускорение поиска по подстроке обычным B-tree; дополнительные индексы вводить по результатам измерений.
- Исключить отдельную загрузку затрат каждого заказа. Зафиксировать выбранную стратегию выборок, тестовый объём и наблюдения без вымышленных SLA.
- Подготовить для выбранного размещения инструкцию резервного копирования и восстановления; проверить восстановление в отдельную тестовую БД до ввода реальных данных.

## Контрольный набор аналитики

| Случай | Что проверить |
|---|---|
| R = 50 000, три расхода 20 000 + 15 000 + 3 000 | Одна строка заказа, R = 50 000, C = 38 000; Backend получает P = 12 000, M = 24% |
| Добавлен заказ R = 10 000, C = 5 000 | Количество 2; R = 60 000; C = 43 000; P = 17 000; общая M = 28,33% |
| Заказ без затрат | Не пропадает из JOIN, C = 0 |
| Нулевая выручка с затратами | Заказ учтён, затраты уменьшают общую прибыль |
| Пустой период | Количество и суммы равны 0, маржа после расчёта null |
| Даты на границах и вне периода | Обе границы включены, внешние даты исключены |
| Все четыре статуса | Включён только completed |
| Изменение затрат/выручки/даты и возобновление | Выборка и итоги сразу соответствуют текущим данным |
| Несколько крупных затрат | Итог превышает лимит одной строки без переполнения и потери копеек |

Автоматизировать интеграционные проверки схемы и аналитики на реальной выбранной СУБД. Покрыть относящиеся к роли T8–T16 общего README; T1–T7 совместно с Backend использовать как проверку соответствия расчётных результатов данным запросов. SQLite не заменяет проверку особенностей PostgreSQL, если выбран PostgreSQL.

## Что передать команде

Схему и ORM-модели, единую цепочку миграций, аналитический слой с описанным интерфейсом, словарь показателей, тесты, вымышленные фикстуры, команды запуска/миграций/проверок, инструкции восстановления и результаты оценки запросов. Файлы общей инфраструктуры передавать TeamLead через согласованные изменения.

## Критерии готовности

- [ ] Схема разворачивается миграциями на пустой БД и защищает целостность данных.
- [ ] Backend использует общие модели, без второй схемы и миграционной цепочки.
- [ ] Отчёт корректно обрабатывает JOIN, пустые затраты, нулевую выручку, даты, статусы и исправления.
- [ ] Строки и итоги согласованы; агрегаты точны и не зависят от пагинации.
- [ ] Проверки выполняются на отдельной БД и воспроизводятся по инструкции.
- [ ] Данные переживают перезапуск; процедура восстановления проверена до работы с реальными данными.
