# CYP — задание Backend

**Рабочая ветка участника:** `feature/backend` (имя из Git, регистр сохранять). Документы с заданиями подготовлены в `docs`.

Основа работы — [общая спецификация](../../../README.md). Этот документ распределяет задачи, не меняя её бизнес-правил. Стек из основного README пока является предложением; его фиксацию и открытые продуктовые решения координирует [TeamLead](../teamlead/README.md).

## Результат работы

Рабочий сервер, через который можно создать клиента и заказ, учесть выручку и затраты, изменить статус и получить согласованные финансовые показатели и отчёт. Данные сохраняются в БД; финансовые результаты не принимаются от клиента как готовые значения.

## Ответственность и границы

| Область | Ответственность Backend |
|---|---|
| API | Маршруты, входные/выходные схемы, ошибки, документация и HTTP-проверки |
| Бизнес-операции | Валидация, статусы, транзакции, обновление дат и обработка отсутствующих записей |
| Расчёты | Канонический расчёт прибыли и маржи на Decimal и его модульные тесты |
| Работа с данными | Сервисы и репозитории, использующие схему и модели DB |
| Отчёт | Проверка параметров, вызов аналитического слоя DB, сериализация результата |

[DB](../db/README.md) владеет схемой, ORM-моделями, миграциями, аналитическими запросами и их интеграционными тестами. Backend не создаёт параллельные модели или цепочку миграций. DB отвечает за корректный состав отчётной выборки и агрегацию; Backend — за единое правило вычисления и округления маржи, HTTP-контракт и выдачу отчёта. [Frontend](../frontend/README.md) получает данные только через API.

## Порядок выполнения

### B1. Зафиксировать контракт до реализации экранов

Совместно с Frontend и DB подготовить контракт; TeamLead принимает его и размещает в будущем `docs/api-contract.md`. Этот путь — ожидаемый результат, файл ещё не создан.

Контракт должен определить:

- Маршруты и методы для списка/карточки/создания/изменения клиентов и заказов, строк затрат, переходов статусов и отчёта. Удаление клиентов и заказов не добавлять.
- Поля запросов и ответов, обязательность, значения по умолчанию, UUID, номер заказа, коды статусов и категорий.
- Имена расчётных полей: выручка, затраты, прибыль, маржа; денежные строки с двумя знаками; маржа — согласованная десятичная строка с двумя знаками либо `null`.
- Поиск, фильтры, сортировку и поведение списка заказов клиента. Если вводится пагинация — параметры, метаданные и итоги по всей выборке.
- Формат ошибок с привязкой к полю; согласованные коды для неверных данных, отсутствующих объектов и запрещённых переходов.
- Формат дат `YYYY-MM-DD` и времени UTC, включительные границы периода и часовой пояс мастерской.
- Примеры успешных ответов, нулевой выручки, пустого отчёта и ошибок. Формат подтверждения завершения в UI не должен подменять серверную валидацию.

### B2. Создать серверную основу

1. После выбора стека создать приложение, конфигурацию, управление соединениями и зависимостями, проверяемый запуск и тестовое окружение.
2. Подключить подготовленные DB модели и миграции; не создавать таблицы автоматически вместо миграций.
3. Разделить HTTP-обработчики, бизнес-сервисы, доступ к данным и чистый расчётный модуль.
4. Параметры БД и режим доступа получать из конфигурации. Примеры переменных передать TeamLead для общего `.env.example`.

### B3. Реализовать операции

- Клиенты: список, карточка с заказами, создание и изменение; имя и минимум один контакт по ограничениям основного README.
- Заказы: список с совместным поиском/фильтром, карточка, создание и изменение; номер назначает сервер с использованием механизма DB, без `MAX(number) + 1`.
- Строки затрат: добавление, изменение и удаление в рамках указанного заказа. Проверять принадлежность строки заказу, чтобы URL одного заказа не изменял затраты другого.
- Проверять точность и диапазоны исходных сумм до сохранения. Не допускать неявного округления лишних знаков БД.
- Реализовать только разрешённые переходы статусов, проверку даты завершения, очистку даты при возобновлении и повторное завершение.
- Отмену выполнять без обнуления сумм; разрешать финансовые исправления завершённого заказа.
- Изменение затрат и `updated_at` заказа выполнять в одной транзакции; ошибки не должны оставлять частичные изменения.
- После успешной операции возвращать актуальные показатели или обеспечить их немедленное получение по контракту.

### B4. Реализовать точные расчёты и отчётный API

- `C = сумма затрат`, `P = R − C`, `M = P / R × 100` при `R > 0`; иначе `M = null`.
- Деньги считать точными десятичными числами. Округлять только конечную маржу, `ROUND_HALF_UP`, два знака; нормализовать отрицательный ноль.
- Не принимать вычисляемые итоги как редактируемые поля и не поддерживать их независимые сохранённые копии.
- Принимать период, проверять порядок дат и передавать его DB. Получать строки, количество и исходные общие суммы из согласованной выборки.
- Общую маржу считать из общей прибыли и общей выручки, не усреднять маржи строк.
- Договориться с DB о точном формате результата аналитического слоя. SQL-агрегации денег остаются точными; отображаемую маржу формирует общий расчётный модуль, а не отдельная формула в каждом обработчике.
- Избежать запроса затрат отдельно для каждого заказа; сверить реализацию с DB.

## Проверки

- Автоматизировать T1–T7 основного README на расчётном модуле, включая копейки, убыток, нулевую выручку и округление `3,125% → 3,13%`.
- Проверить API для F1–F10: создание/изменение, контакты, лимиты текста и сумм, все разрешённые и запрещённые переходы, отсутствующие ссылки и принадлежность затрат.
- Совместно с DB проверить T8–T16: агрегаты, даты, статусы, исправления, перезапуск и отсутствие частичных записей.
- Проверить HTTP-ответы для пустого отчёта и нулевой общей выручки; согласованность карточки, списка и отчёта после исправления завершённого заказа.
- Тесты используют отдельную тестовую БД и вымышленные данные. Команды и зависимости фиксируются в проекте.

## Что передать команде

- Исходный код сервера, файлы зависимостей, тесты и фактически проверенные команды запуска/проверок.
- Реализованный контракт и примеры ответов для Frontend; описание всех изменений контракта.
- Интеграцию аналитического слоя DB без повторной независимой реализации отчётной выборки.
- Список конфигурационных параметров и ограничений; статус реализации выбранной модели доступа.

## Критерии готовности

- [ ] Через API выполняются UC-1–UC-6; реализованы относящиеся к серверу F1–F10.
- [ ] Проходят расчётные, HTTP- и согласованные интеграционные проверки; ошибки не оставляют частичных данных.
- [ ] Суммы и маржа сериализуются по контракту без потери точности.
- [ ] Сервер запускается на чистой БД после миграций DB; данные переживают перезапуск.
- [ ] Frontend может работать по реальному API; расхождения документации устранены.

Начинать с контракта и расчётного модуля. Операции хранения подключать после получения схемы DB. Спорные продуктовые решения передавать TeamLead, не менять их локально в коде.
