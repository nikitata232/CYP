# CYP — задание Frontend

**Рабочая ветка участника:** `feature/frontend` (имя из Git, регистр сохранять). Документы с заданиями подготовлены в `docs`.

Основа работы — [общая спецификация](../../../README.md), особенно разделы 2–8 и UC-1–UC-6. Этот README задаёт область реализации интерфейса. Предлагаемый стек React + TypeScript + Vite фиксируется с [TeamLead](../teamlead/README.md) до инициализации.

## Результат работы

Русскоязычный интерфейс, в котором владелец мастерской проходит путь: клиент → заказ → выручка и затраты → завершение → отчёт. Все основные действия выполняются через интерфейс и реальный API, без редактирования БД.

## Ответственность и границы

Frontend отвечает за экраны, формы, навигацию, обработку ошибок, форматирование и актуальность отображаемых данных. [Backend](../backend/README.md) отвечает за серверную валидацию и операции; [DB](../db/README.md) — за хранение и аналитические выборки. Финальные показатели и общие итоги берутся с сервера.

Не подключаться к БД из браузера, не рассчитывать отчёт по загруженной странице таблицы, не создавать собственную трактовку маржи. Макеты общего README задают состав данных, но не готовый дизайн. Визуальное решение согласовать с TeamLead в рамках MVP.

## Порядок выполнения

### FE1. Согласовать API и основу интерфейса

1. Совместно с Backend определить контракт: поля, маршруты, ошибки, денежные строки, даты, `null` для маржи и обновление данных после операций.
2. Передать TeamLead требования к навигации, адресу API и окружению разработки.
3. Создать приложение, маршруты и общий API-клиент с обработкой ошибок. Не дублировать запросы и типы по экранам.
4. Подготовить общие элементы: денежное поле, отображение денег/маржи/статуса, форма, подтверждение, загрузка, пустое состояние и ошибка.
5. До готовности API допустимы явно обозначенные моки по согласованному контракту. Финальная приёмка проходит с настоящим сервером; мок не должен незаметно заменять неудачный запрос.

### FE2. Заказы

- Список: номер, название, клиент, статус, выручка, затраты, прибыль, маржа; переход в карточку.
- Совместные поиск по номеру/названию/имени клиента и фильтр статуса; по умолчанию все статусы. Сортировка соответствует общей спецификации.
- Создание: название, выбор существующего клиента или создание нового с последующим выбором; описание и выручка; начальный статус задаёт сервер.
- Карточка: контакты клиента, реквизиты заказа, статус, четыре финансовых показателя и список затрат.
- Редактирование выручки, названия, описания и клиента отдельной явной формой.
- Затраты: добавить/изменить категорию, описание и сумму, удалить после подтверждения. Не предлагать удаление заказа или клиента.
- Статусы: показывать только допустимые действия текущего состояния; при завершении показать актуальные суммы, запросить подтверждение и дату. Дата по умолчанию — сегодня в часовом поясе мастерской.
- Возобновление и восстановление соответствуют диаграмме статусов. После операции брать актуальный статус и дату с сервера.
- Для незавершённых заказов показывать, что финансовые показатели предварительные; при убытке использовать знак минус и текст, а не только цвет.

### FE3. Клиенты

- Список клиентов с именами и контактами, создание и изменение.
- Имя обязательно; нужен телефон и/или другой контакт. Длина и правила совпадают с сервером. Не требовать уникальности контактов.
- Карточка клиента показывает контакты и связанные заказы со ссылками.
- После изменения клиента обновлять затронутые отображения имени и контактов, включая карточки и списки заказов.

### FE4. Отчёт

- Фильтр начальной и конечной даты с включительными границами; по умолчанию текущий месяц в часовом поясе мастерской.
- Итоги: количество заказов, выручка, затраты, прибыль, общая маржа.
- Таблица: номер, название, клиент, дата завершения, выручка, затраты, прибыль, маржа; ссылка в заказ.
- Пояснить, что отчёт включает завершённые заказы по дате завершения и отражает текущие исправленные данные.
- Не добавлять произвольные графики, аналитику по клиентам, экспорт, план-факт и движение денег.
- Если появится пагинация, показывать серверные итоги по всей выборке, а не по видимой странице.

### FE5. Деньги и состояния

- Ввод принимать с точкой или запятой; исходные суммы передавать десятичными строками, без преобразования через `Number` для арифметики денег. Не округлять лишние знаки молча.
- Отображать рубли и копейки в русском формате. Для больших сумм использовать форматирование, сохраняющее точность исходной строки.
- `null` маржи показывать как «—», нулевую маржу — как `0,00%`; отрицательные значения не скрывать. Маржа — процент, не денежная сумма.
- Предварительный расчёт в форме необязателен. При его наличии использовать точную арифметику и явно отделять несохранённое состояние; после сохранения принимать серверные показатели.
- Для экранов предусмотреть загрузку, ошибку с повтором, отсутствие данных и отсутствие результатов поиска.
- При ошибке сохранения оставлять ввод и показывать ошибки полей; блокировать повторное нажатие во время отправки.
- После изменений обновлять карточку, список, клиента и затронутый отчёт; не оставлять старые суммы в клиентском кэше.
- При быстрой смене фильтров не позволять запоздалому ответу заменить более свежий результат.
- Формы снабдить подписями и доступными сообщениями ошибок; основные действия должны работать с клавиатуры. На узком экране допустима прокрутка таблицы, формы и показатели помещаются по ширине.

## Проверки

- Пройти UC-1–UC-6 с реальным API, включая изменение материалов с 20 000 до 22 000 ₽ и обновление маржи с 24% до 20%.
- Проверить T17: ошибка сервера не уничтожает ввод и не показывает ложный успех.
- Проверить отображение убытка, нулевой выручки, пустого отчёта, копеек, больших сумм и маржи `null`.
- Проверить поиск вместе со статусом, смену периода, граничные даты, возобновление заказа и повторное завершение.
- Проверить загрузку, повтор запроса, повторное нажатие сохранения и работу на узком экране.
- Добавить согласованные автоматические проверки критичных форматов, состояний и сквозного сценария. Инструменты выбрать с TeamLead; не подменять проверку интеграции одними моками.

## Что передать команде

Исходный код, закреплённые зависимости, команды разработки/сборки/проверок, описание необходимых переменных, список экранов и результаты проверки с реальным API. Изменения контракта предварительно согласовывать с Backend и TeamLead.

## Критерии готовности

- [ ] Реализованы «Заказы», карточка заказа, «Клиенты», карточка клиента и «Отчёт».
- [ ] UC-1–UC-6 выполняются полностью через интерфейс и реальный API.
- [ ] Форматирование не теряет точность; суммы и итоги совпадают с сервером.
- [ ] После исправления завершённого заказа все затронутые представления обновляются.
- [ ] Ошибки, пустые состояния, подтверждения и узкий экран проверены.
- [ ] Сборка и согласованные проверки проходят; команды воспроизводимы.
